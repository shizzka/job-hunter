# План улучшения job-hunter для повышения шанса ответа на резюме

Дата: 2026-07-09  
Цель: повысить не просто количество откликов, а конверсию в просмотры, ответы HR, приглашения и собеседования.

## Статус на 2026-07-10

Реализованы базовые слои P0-P2: расширенная analytics/funnel, cluster/resume/cover metadata, response_probability_score, HH questionnaire analytics и типовые ответы, CLI/Telegram сводки.

Отдельно закрыт этап retry logic:

- retry_reason теперь различает `rejected`, `viewed_no_response`, `not_viewed`, `silence`;
- для `viewed_no_response` и `not_viewed` есть отдельные delay env;
- добавлен дневной лимит retry-откликов;
- добавлен лимит retry на компанию за окно дней и ручная company blocklist;
- в Telegram manual/yellow-zone карточках есть кнопка `Не трогать компанию`;
- добавлен CLI preview `./run.sh retry-preview` для просмотра retry-кандидатов без откликов;
- повторные попытки пишут `retry_reason/retry_outcome` в analytics;
- electrician resume не выбирается как следующий вариант;
- retry stats выводятся в CLI/Telegram analytics.

## Общий принцип

Сейчас бот уже умеет искать, фильтровать, откликаться, писать сопроводительные, отвечать на HH-анкеты, вести часть диалогов и работать с несколькими резюме. Следующий этап должен быть не про "больше спама", а про управляемую систему:

1. измеряем, какие действия реально дают просмотры и ответы;
2. разделяем вакансии на понятные кластеры;
3. под каждый кластер выбираем резюме, сопровод, уровень агрессивности и стратегию повторного отклика;
4. снижаем ручную нагрузку: в Telegram отправляем только важные исключения и решения;
5. регулярно улучшаем базу знаний, анкеты и тексты на основании фактических исходов.

  - отказ;
  - приглашение;
  - входящее сообщение;
  - ответ бота в чат;
  - повторный отклик другим резюме;
  - молчание N дней.
- Для каждой вакансии сохранять признаки:
  - source;
  - vacancy_id;
  - title;
  - company;
  - cluster;
  - score релевантности;
  - score вероятности ответа;
  - resume_variant;
  - cover_style;
  - salary;

  - required_experience;

  - были ли вопросы работодателя;
  - сколько вопросов заполнено;

  - конверсия отклик -> просмотр;
  - просмотр -> ответ;
  - ответ -> приглашение;

Критерии готовности:

Ожидаемый эффект:

- Появится понимание, где реальные ответы, а где бот просто тратит лимиты и время.

## P1. Второй score: вероятность ответа

Сейчас matcher в основном оценивает соответствие кандидата вакансии. Нужен отдельный score: стоит ли вообще тратить попытку.

Признаки для `response_probability_score`:

- сколько откликов уже есть;
- свежесть вакансии;
- дата публикации / обновления;
- точность совпадения уровня;
- junior/junior+ против middle/senior;
- наличие явного "готовы обучать";
- наличие "без опыта";
- удаленка/регион;
- зарплатная вилка;
- размер компании;
- шаблонные массовые вакансии;
- рекрутерская активность;
- уже были отказы/молчание от этой компании;
- похожие вакансии этой компании раньше отвечали или нет.

Решение по двум score:

- `match_score`: насколько кандидат подходит.
- `response_probability_score`: насколько вероятно, что ответят.

Пример:

- match 80, response 20: вакансия хорошая, но 800 откликов и 3+ года опыта - возможно skip или ручной.
- match 62, response 80: junior-friendly, свежая, мало откликов - можно пробовать.
- match 50, response 75: yellow-zone, отправить в Telegram на "норм/мимо".

Критерии готовности:

- В каждом решении видны оба score.
- Порог автоотклика использует оба score.
- Есть статистика, какой score лучше предсказывает просмотр/ответ.

Тесты:

- Unit-тесты scoring-функции.
- Snapshot-тесты на реальные вакансии из логов.
- Проверка, что высокий match не пробивает жесткие red flags.

Ожидаемый эффект:

- Меньше откликов туда, где шанс ответа низкий.
- Больше попыток на "окологодовые" вакансии, где могут взять junior+.

Ожидаемый эффект:

## P2. Повторные отклики и молчание

Повторное резюме нужно отправлять не только на отказ, но и на молчание, но аккуратно.

Что нужно сделать:

- Классифицировать исходы:
  - `rejected`;
  - `ignored_7d`;
  - `ignored_14d`;
  - `viewed_no_response`;
  - `not_viewed`;
  - `message_received`;
  - `invited`.
- Настроить retry policy:
  - отказ: другое резюме только если вакансия подходит и отказ не явно финальный;
  - молчание 7-14 дней: другое резюме, если вакансия высокая по match/response score;
  - просмотрено без ответа: возможно короткий follow-up, если чат открыт;
  - не просмотрено: можно повторить другим резюме, но лимитировать.
- Не отправлять electrician resume.
- Не повторять больше N раз на одну компанию/вакансию.
- Сохранять resume_variant и retry_reason.

Критерии готовности:

- В analytics видно, почему был повтор.
- В Telegram можно увидеть краткую сводку: "отправил другое резюме по молчанию".
- Есть дневной лимит retry-откликов.

Тесты:

- Unit-тесты retry policy.
- Regression: electrician resume не выбирается.
- Regression: повтор не идет на archived/closed.

Ожидаемый эффект:

- Больше шансов по вакансиям, где первый отклик не сработал.
- Меньше ручного контроля.

## P3. База знаний кандидата

Бот должен лучше понимать реальные навыки, не занижая и не завышая.

Факты, которые стоит явно хранить:

- около года тестирования;
- участие в разработке автотестов;
- Python/pytest на базовом уровне;
- Postman/Swagger/API;
- JSON/XML;
- HTTP;
- SQL базово;
- DevTools;
- баг-репорты;
- чек-листы;
- тест-кейсы;
- участие в автотестах, но не позиционировать как уверенный AQA;
- техническое образование;
- опыт руководства командой в электрике как soft/management background;
- текущая зарплата/ожидания: итоговая зарплата зависит от загрузки и формата.

Что нужно сделать:

- Разделить facts на:
  - confirmed;
  - inferred;
  - weak;
  - do_not_claim.
- В prompt давать LLM только релевантные facts.
- Для каждого факта указать разрешенные формулировки.
- Добавить запретные формулировки.

Критерии готовности:

- LLM не завышает AQA.
- LLM не забывает техническое образование.
- LLM корректно использует опыт руководства командой.
- LLM не пишет electrician как текущую цель.

Тесты:

- Snapshot-тесты генерации сопроводов.
- Тесты на forbidden claims.
- Тесты на facts filtering.

Ожидаемый эффект:

- Более правдоподобный кандидат.
- Меньше отказов из-за несоответствия ожиданий.

  - AQA, если junior/trainee и Python допустим;
  - middle, если требования "от 1 года" или явно готовы доучивать.

Критерии готовности:

- На истории последних откликов нет явных мимо.
- "Окологодовые middle" не режутся автоматически.
- У фильтра есть объяснение в analytics.

Тесты:

- Regression-тесты на реальные плохие вакансии из логов.
- Regression-тесты на хорошие junior+/middle-light вакансии.

Ожидаемый эффект:

- Меньше мусорных откликов без падения охвата.

## Метрики успеха

Основные:

- отклик -> просмотр;
- просмотр -> сообщение;
- сообщение -> приглашение;
- приглашение -> собеседование;
- отклик -> отказ;
- отклик -> молчание 14 дней.

Вспомогательные:

- число автооткликов в день;
- число ручных вмешательств;
- число падений apply;
- число незаполненных анкет;
- доля fallback-сопроводов;
- доля overclaim guard;
- среднее число LLM-вызовов на отклик;
- стоимость/лимиты LLM;
- число Telegram-уведомлений в день.

Целевые изменения:

- меньше мусорных откликов;
- выше доля просмотров;
- выше доля ответов;
- меньше ручных действий;
- меньше падений на анкетах;
- больше понимания, какие резюме и тексты реально работают.

## Риски

- Слишком агрессивные фильтры снова снизят количество откликов.
- Слишком мягкие фильтры вернут мусор: сервисные инженеры, техподдержка, разработчики.
- LLM может завышать опыт автоматизации.
- Повторы другим резюме могут выглядеть странно, если делать часто.
- HH может менять DOM анкет.
- Telegram может стать шумным, если отправлять все детали.

Как снижать риски:

- все новые стратегии включать флагами;
- добавлять тесты на реальные ошибки из логов;
- запускать live smoke-test на 1 вакансии перед daemon;
- смотреть воронку минимум 7 дней до выводов;
- не менять одновременно резюме, фильтры и сопроводы без маркировки в analytics.
