# Направления поиска

Направление — надстройка внутри профиля: набор вариантов резюме, поисковые запросы,
ключевые слова и политика профессии `qa` или `generic`. Один профиль соответствует
одной учётной записи hh. Cookies, seen-вакансии, лимиты, чаты и переговоры общие
для всех её направлений; новый профиль для другого резюме той же учётки не нужен.
Биографические факты кандидата остаются общими. Позиционирование, цель и разрешённые
формулировки роли задаются в направлении. KB-RETRIEVE отбирает релевантные
факты из knowledge, а `[DO_NOT_CLAIM]` и `[LIMIT]` обязательны при любом выборе.
Допуски, группа электробезопасности и сроки их действия требуют подтверждения
источниками; название вакансии их не подтверждает.

**Патчинг резюме под вакансию не делаем.** Скачивание выполняется только чтением
серверного HTML. Бот не меняет резюме на hh: работодателю доступна его текущая
версия. A/B здесь означает выбор между уже существующими резюме.
`hh_resume_pipeline.py` — отдельный старый механизм повторных откликов; к A/B
не относится и в DIR-2 не изменяется.

## Хранение и совместимость

Внутри `profiles/<p>/` (для default — внутри его home):

- `directions/<name>.json` — валидируемое описание направления;
- `directions/<name>/<sha256>.md` — неизменяемые версии скачанного текста;
- `directions_state.json` — `{"active_direction": "<name>"}`.

Поля описания:

```json
{
  "name": "electrical",
  "title": "Электрика",
  "filter_policy": "generic",
  "positioning": "Электромонтажник. Монтирую кабельные линии и собираю щиты.",
  "goal": ["Электромонтажник", "Электрик"],
  "allowed_wording": ["Электромонтажник"],
  "do_not_claim_extra": ["Действующая группа электробезопасности не подтверждена"],
  "search_queries": ["электрик", "электромонтажник"],
  "relevant_keywords": ["электрик", "электромонтаж"],
  "exclude_keywords": [],
  "selection_strategy": "ab",
  "work_conditions": {
    "allowed_formats": ["remote", "hybrid", "on_site", "field"],
    "allow_fly_in_fly_out": false,
    "allowed_cities": []
  },
  "variants": [{
    "hh_resume_hash": "example_hash",
    "hh_resume_numeric_id": 123456,
    "title": "Электрик",
    "text_file": "directions/electrical/<sha256>.md",
    "text_sha256": "<64 hex символа>",
    "fetched_at": "2026-10-17T10:00:00+00:00",
    "tags": [],
    "status": "active"
  }]
}
```

Пример схематический: hash, numeric id, путь и SHA нужно получить из скачивания.
`hh_resume_numeric_id` может быть `null`, если HTML не содержит однозначной связи
hash ↔ числовой id. Идентификатор не угадывается по заголовку или произвольному
полю `id`. Такой вариант можно выбирать, но его переговоры останутся в статистике
несопоставленными до получения достоверного id. Дополнительные необязательные
поля: `application_mode` (`preview|confirm|auto`), `cover_letter_fallback` (текст).
Без своего `cover_letter_fallback` направление использует нейтральное резервное
письмо: профильный шаблон другой профессии не переносится автоматически.
Путь текста ограничен каталогом данного направления. SHA проверяется перед
использованием; повреждённое или отсутствующее резюме останавливает обработку.

Сохранение JSON и указателя активно выбранного направления атомарное. Тексты
адресуются по содержимому: подготовка нового текста не перезаписывает версию,
с которой уже оценивалась вакансия. При загрузке активное направление накладывает
запросы, keywords, политику, резюме и необязательный режим поверх `profile.env`.
Регионы и графики поиска (`SEARCH_PROFILES`) остаются настройками профиля.
Быстрый поиск также использует запросы активного направления, включая тип `qa`.
Корень фактов и состояния остаётся корнем профиля, а не папкой текста варианта.

Условия работы направления редактируются через «Что ищу → Изменить»:
«Допустимые форматы работы», «Разрешена ли вахта», «Города места работы».
Изменения действуют после сохранения. Для новых и старых направлений без
`work_conditions` вахта запрещена, форматы разрешены все. Если собственные
`search_profiles` направления содержат только `schedule=remote`, начальные
форматы — удалённо и гибрид. Чтение старого файла подставляет эти значения
без перезаписи; при следующем сохранении они записываются в направление.
Явные условия не меняются при редактировании поисковых запросов и регионов.

`allowed_cities` — необязательный список полных названий городов места работы;
пустой список не ограничивает города. Он проверяется по `address.city` HH,
а не по региону публикации. Полностью удалённая работа освобождена от этой
проверки. Если город нужен, но HH его не указал, вакансия идёт на разбор.
Несколько форматов HH считаются альтернативами; достаточно разрешённого.

Общая проверка читает `workFormats` / `work_format`, `@workSchedule` / `schedule`,
`employmentForm`, `flyInFlyOutDurations`, `compensation.mode` / `salary_range.period`
из состояния поисковой выдачи и самой вакансии. На странице также читаются
поля `work-formats-text`, `common-employment-text` («Вахта на N смен»),
`vacancy-salary` («за вахту»). Название и описание могут только отправить вакансию
на разбор из-за упоминания вахты. График полного дня или сменный график сам по
себе не доказывает работу на месте. Неизвестный формат → «формат не указан»,
без оценки и без отправки отклика. Запрещённые условия отсекаются до оценки,
письма и карточки подходящей вакансии, включая ручную очередь и повторные отклики.

Перед отправкой обычной формы и анкеты работодателя выполняется свежий GET
страницы этой вакансии в той же HH-сессии, без выполнения её скриптов и без
навигации открытой формы. Перенаправления не разрешены; проверяются владение
браузером и неизменность авторизации. Недоступные условия блокируют отправку.
Прежние защиты неизвестных окон, однократной отправки и неопределённого исхода
сохраняются. Окно HH с вопросом о вахте остаётся под защитной остановкой:
без проверенной структуры и безопасного закрытия бот не отвечает и не меняет резюме.

При заполненном позиционировании/цели направления старый `profile_note` и разделы
`[GOAL]`/«Карьерная цель» исключаются из контекста оценки, писем и анкет, а поля
`target_roles`, `positioning` и `allowed_wording` общих facts заменяются намерением
этого направления. Исключение безопаснее пометки «другие направления»: модель не
получает конкурирующую цель и не отбрасывает вакансии электрика ради QA.
Общие `[DO_NOT_CLAIM]`/`[LIMIT]`, включая запреты внутри прежнего profile_note,
сохраняются, к ним добавляются запреты направления. Позиционирование (до 1500
символов) обязательно входит в KB-RETRIEVE; grounding получает тот же снимок
источников и видит его как `profile_note`. При выключенном retrieval направление
тоже использует безопасный локальный отбор с обязательными ограничениями.
ИИ предлагает черновик позиционирования, цели и формулировок по текстам выбранных
резюме и общим подтверждённым фактам; пользователь проверяет и сохраняет его.
Пустые новые поля сохраняют прежнее поведение.

Без активного направления профиль загружается и работает как прежде. Создание
направлений не мигрирует профили автоматически. Временный отдельный профиль
`electrician` не меняется. Переход на направления выполняет сам владелец через
подтверждённый черновик. Общая база knowledge и ограничения симлинков из DIR-1
сохраняются; факты разных кандидатов не объединяются через меню направлений.

## Меню Telegram

Кнопка **«🎯 Направления»**, команда `/directions` доступны администратору и клиенту.
Клиент всегда работает только внутри своего профиля; администратор — внутри
выбранного административного профиля. Аргументы команд направлений не выбирают
чужой профиль.

1. Список показывает активное направление. Для переключения отправить номер и
   подтвердить «Сохранить направление».
2. «Новое направление» читает полный каталог резюме из текущей HH-сессии, без
   прежнего фильтра названий QA-профиля. Отправить один или несколько
   номеров, например `1 3`. Бот проверяет их принадлежность текущей HH-сессии,
   скачивает тексты только чтением и через ИИ предлагает название, запросы,
   подходящие/исключающие слова и тип фильтра. ИИ проходит существующую проверку
   доступа и учёта использования `_authorize_ai_usage`.
3. Черновик можно сохранить, изменить или отменить. Для правок есть
   `/direction_edit title|queries|relevant|exclude|filter`. Сначала команда с полем,
   затем новое значение; запросы — по одному в строке, keywords — через запятую.
4. Варианты: `/direction_add`, `/direction_remove`, `/direction_pause`,
   `/direction_resume`. Номера принимают несколько значений. Меню сохраняет хотя
   бы один активный вариант. «Варианты направления» и `/search_resume` позволяют
   поставить выбранный активный вариант первым и включить `single`.
5. `/direction_refresh` обновляет скачанные тексты, `/direction_suggest` повторяет
   анализ, `/direction_single` и `/direction_ab` меняют стратегию. Все изменения
   сначала показываются как черновик и требуют сохранения.

При активном направлении старые кнопки `/refresh_resume` и `/grabresume` тоже
готовят черновик обновления вариантов. CLI-команды обновления/скачивания и старый
импорт при входе HH отказываются перезаписывать тексты активного направления:
обновление выполняется через `/direction_refresh` с подтверждением.

Черновик не меняет действующие JSON, тексты, state или `profile.env` до «Сохранить».
Он привязан к пользователю, профилю и версии исходного активного направления;
при смене контекста устаревший черновик нельзя применить. Неопубликованные тексты
хранятся в памяти бота, поэтому перезапуск отменяет такой черновик.
Сохранение ждёт завершения активной разовой команды профиля. Работающий процесс
также сверяет сохранённое направление перед оценкой, письмом и диспетчеризацией:
изменение настроек другим процессом требует перезапуска поиска.

`/search_resume`, `/search_suggest`, `/search_edit`, `/search_use_draft` работают
с активным направлением. При его отсутствии сохраняется прежний сценарий команд.
Первое сохранённое направление становится активным; последующие создаются
отдельно и включаются через переключение. После сохранения бот перезапускает
повторный поиск, если он работал.

## Выбор варианта и запись отклика

`single` выбирает первый активный вариант. `ab` вычисляет
`int(SHA256(str(vacancy_id)), 16) % N` среди активных вариантов в порядке списка.
Варианты на паузе исключаются. Выбор повторяем при одинаковом составе и порядке
вариантов; изменение состава/порядка меняет распределение будущих вакансий.
На большом наборе id распределение приблизительно равномерное, а не строго
поровну в каждой небольшой группе. `closest` зарезервирован в интерфейсе и
не реализован; его нельзя сохранить как действующую стратегию.

Выбор фиксируется перед оценкой вакансии. Оценка, письмо и нативные вопросы
отклика используют один выбранный текст без изменения глобального конфига под
каждую вакансию. Очередь ручного отклика сохраняет эту привязку. При смене
профиля/направления, паузе/удалении варианта или изменении его текста старая
привязка не превращается в другой вариант автоматически: нужна новая оценка.

Существующие attempt/outcome/decision записи получают дополнительные поля:
`direction`, `hh_resume_hash`, `hh_resume_numeric_id`, `variant_text_sha256`,
`selection_strategy`, `selection_reason`, `direction_variant_scope`.
Последнее равно `requested_local_variant`: это выбранный локально и запрошенный
при отправке вариант, **не доказательство фактической доставки этого резюме**.
SHA локальных входов оценки и письма по-прежнему пишется отдельно. Отправка,
сверка, claim/idempotency и границы подтверждения доставки не меняются.

## Статистика A/B

Администратор получает краткий отчёт `/direction_stats` и CSV `/direction_csv`.
Оба читают только локальный `negotiation_snapshots.jsonl` текущего профиля, не
обращаются к hh и не строят воронку по `analytics_events`. Программный интерфейс:
`direction_stats.summarize(home_dir, snapshots=None)` и `export_csv(summary)`.
Для сбора снимков есть отдельный существующий инструмент:

```bash
venv/bin/python -m hh.negotiation_snapshot --profile <profile>
venv/bin/python -m hh.negotiation_snapshot --profile <profile> --archived
```

Эти две команды выполняют чтение hh; тесты их не запускают. Отчёт отражает только
уже собранные темы; без снимков числа нулевые. Для каждой темы берётся последнее
наблюдение по `fetched_at`, затем `resumeId` сопоставляется с сохранённым
`hh_resume_numeric_id`. Повторные снимки одной темы не увеличивают число откликов.

- `applied` / откликов — темы с явным происхождением ответа соискателя;
- `viewed` / просмотрено — `viewedByOpponent=true`;
- `rejected` / отказ — явный статус отказа;
- `next_stage` / следующий этап — явное приглашение, интервью, тест, оффер и т.п.;
  начальный `SCREENING` сам по себе не считается переходом работодателя;
- `no_response` / без ответа — отклик без явного отказа или следующего этапа.

Темы, закрытые самим соискателем (`declinedByApplicant`), не считаются отказами
работодателя и не входят в «без ответа».

Просмотрено и без ответа могут пересекаться. Это наблюдаемое состояние тем,
не число всех попыток отправки и не причинная оценка качества резюме. Входящие
приглашения могут иметь просмотры/этапы, но не увеличивают `applied`. Неизвестные
numeric id идут в `unmatched`; id, повторённые между направлениями, — в
`ambiguous`. Их исходы не приписываются произвольному варианту. Удаление варианта
из описания лишает старые темы его соответствия; пауза сохраняет соответствие.
Снимок не хранит исторический текст hh, поэтому нельзя приписывать старому
отклику текущую SHA текста и сравнивать обновления одного hh-резюме как разные
A/B группы. Для A/B нужны отдельные hh-резюме.
