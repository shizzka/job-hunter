# QUEUE-1: очередь команд профиля

Изменяется только оркестрация Telegram-бота. Agent, HH, durable claim,
проверки доставки, matcher и фоновые циклы демона не изменены.

## Классификация

| Команда / действие | Категория | Обоснование |
| --- | --- | --- |
| `/search`, в том числе поиск из `captcha_retry` | Периодическая, coalesce по `search` | Повторный запуск поиска уже running/waiting не нужен; правило владельца. |
| `/dryrun` | Периодическая, отдельный ключ `dry-run` | Повторный одинаковый тестовый прогон объединяется; с настоящим поиском не объединяется. |
| `/check` | Периодическая, `check invitations` | Один проход проверки инвайтов/синхронизации переговоров; повтор running/waiting объединяется. |
| `/digest` | Периодическая, `digest` | Повторная генерация одинакового периодического дайджеста объединяется. |
| «Откликнуться с ИИ» / manual token | Ручная, каждое нажатие отдельно | Каждая запись повторно попадает в обычный CLI/agent с проверками кандидата, approval и claim. |
| `/chat_ai`, `/ai_chat`, `/chat_answer`, список чатов, reply/alternative/send, включая manual варианты | Ручная, без coalesce | Нельзя терять явно запрошенный ответ/вариант/отправку. |
| Google Form preview/submit, `gf:check` / `gf:send` | Ручная, без coalesce | Повторяется исходный callback, включая проверку ревизии и текущих ответов перед submit. |
| `/analyze`, `/backfill`, `/grabresume`, `/refresh_resume`, `/search_suggest` | Ручная, без coalesce | Явно запрошенная работа; неоднозначные команды сохранены отдельно. |
| `/hh_auth`, `/client_hh_auth`, callback восстановления HH | Вне очереди: явное восстановление | Доступно при паузе очереди, чтобы можно было восстановить сессию. Использует то же резервирование профиля; при активной/запускаемой команде отклоняется. Не исполняется автоматически. |
| `/daemon_on`, `/daemon_off`, repeat presets/off | Вне очереди: управление процессами | Сохраняют защиту занятости, в том числе при резервировании/ожидающих задачах; не могут запустить демон между проверкой и запуском queued задачи. |
| Меню, `/busy`, `/status`, статистика, `/cancel_active`, редактирование настроек/полей формы, feedback/snooze/block | Вне очереди: интерфейс/управление | Не создают фоновой задачи профиля. Прежние ограничения редактирования формы при занятости сохранены. |
| `/hh_responses`, `/hh_response_count` | Вне очереди: существующий HTTP-счётчик | Существующая операция чтения, не запускает browser agent; её прежний способ выполнения сохранён. |
| Daemon full-search, fresh-search, check | Вне памяти очереди бота | Уже выполняются отдельным процессом в собственном цикле; fresh-search не имеет команды запуска в Telegram. Их расписание не меняется. |

Карта команд бота: `telegram_bot.py:2816` в исходной версии v0.8.2;
актуальная классификация admission: `telegram_app/command_queue.py:25`.
Бот не имеет отдельной команды проверки почты: инвайты и переговоры проверяет `/check`.

## Приём, запуск и повторные проверки

- `telegram_app/command_queue.py:66`: декоратор сохраняет исходный dispatch/callback,
  а не готовый subprocess как замену callback-проверкам.
- `telegram_app/command_queue.py:186`: admission; FIFO отдельно для каждого профиля,
  coalesce только четырёх перечисленных ключей, лимит ожидающих записей.
- `telegram_app/command_queue.py:129`: при dequeue заново разрешается текущий
  пользователь и проверяется доступ к исходному профилю. Смена выбранного профиля
  для queued dispatch приводит к пропуску, а не запуску на другом профиле.
- `telegram_app/command_queue.py:317`: единственный drainer профиля проверяет TTL,
  паузу/guard и вызывает сохранённый исходный путь.
- Исходные `TelegramCallbackRouter._handle_callback_query`, `TelegramBot._dispatch`,
  `_start_manual_ai_apply`, `_start_chat_ai_reply`, `_start_google_form_command`,
  `_start_cli_command` снова выполняют свои проверки. CLI manual token и form
  approval revision передаются агенту как при немедленном запуске. Claims и отправка
  не реализуются в боте заново.
- `telegram_app/subprocesses.py:106` и `:33`: clear и prune будят очередь.
- `telegram_app/subprocesses.py:135`: создание runner и вход в него запрещены после
  остановки, включая ИИ-подбор запросов без subprocess.

Между проверкой свободного слота и резервированием, а также между выбором головы
очереди и резервированием нет `await`. Во время асинхронных проверок слот занят
`_queue_launching`. Новая запись добавляется в хвост даже между clear и запуском
drainer. Вложенные вызовы узнают владельца резервирования по task-local context;
фоновые runner не получают права обходить admission от родительской задачи.
Восстановление сессии использует тот же слот, но является явным действием вне FIFO.
Параллель разных профилей сохранена.

## Кнопки, TTL, отчёт

`BOT_COMMAND_QUEUE_MAX=10`, `BOT_COMMAND_QUEUE_TTL_MINUTES=120` (см. env example).
Вместимость относится к ожидающим записям. TTL проверяется при попытке запуска;
пауза сама по себе не списывает запись до возобновления или удаления владельцем.

Кнопка manual apply снимается после принятия либо запуска, возвращается при TTL,
удалении, отказе запуска, ошибке и штатном сбросе. Сохраняется исходная клавиатура;
если её не было в callback, восстанавливается кнопка с исходным callback payload.
Постановка сообщает номер, текущую команду и отдельную кнопку удаления записи.
Удаление проверяет owner user id; admin может удалить чужую запись.

После исчерпания очереди каждому участвовавшему чату приходит один отчёт только
по его записям: метка и короткий исход. Подтверждение HH и неопределённый исход
берутся из того же formatter, что в обычном результате. Для отказа manual без
stdout дополнительно читается статус карточки. Отчёт не отправляется при паузе,
пока очередь не завершилась или все записи не сняты. Исходная активная команда,
которая не ожидала в очереди, в число queued задач не входит.

## Источники паузы

`telegram_app/command_queue.py:416` снимает inode/offset профильных run history,
analytics и логов до команды; `:427` читает только новые записи после неё:

- `hh_recovery.stopped/reason`, `source_stats.hh.stop_reason`;
- `error_kind=HHUnexpectedUI`, `error=hh_unexpected_ui`, остановленный
  `hh_ui_isolation`, manual event `note=manual_ai:hh_ui`;
- явные признаки hard stop/auth/captcha в stdout/stderr и новых строках логов.
  Это необходимо для `/check`: «Не залогинен!» записывается в лог даже при exit 0;
- structured `hh_hard_stop`, `anti_bot_kind`, `auth_required`, если предоставлены
  транспортом результата.

`telegram_app/command_queue.py:283` дополнительно проверяет pending captcha и
`<profile.home_dir>/hh_guard_state.json`: будущий `blocked_until` блокирует запуск,
повреждённое/нечитаемое состояние также ставит очередь на паузу. Глобальный config
профиля не переключается. Лимит автооткликов остаётся ответственностью обычных
agent guards; поле `blocked` HH guard означает cooldown, а не исчерпание квоты.

Следующая запись остаётся на месте. Владельцу/ожидавшим чатам приходит одно
уведомление с причиной и «Продолжить очередь». Кнопка имеет стабильный token,
не зависящий от удаления первой записи. Resume снова проверяет guard и доступ,
не снимает HH cooldown. `captcha_retry` остаётся явным пользовательским снятием
cooldown; в очередь помещается только поиск после этого действия, поэтому
отложенный запуск не повторяет снятие более нового cooldown.

## Перезапуск и ограничения

`telegram_app/command_queue.py:396`: штатная остановка запрещает новые runner,
отменяет drainer, сообщает ожидавшим чатам о сбросе и возвращает кнопки best-effort,
до закрытия Telegram sessions. Отдельно учтены зарезервированные задачи,
ещё ожидающие доставку progress. После рестарта очередь пуста и ничего сама
не запускает.

При SIGKILL, падении процесса/машины или недоступности Telegram уведомления и
восстановление кнопок гарантировать нельзя: память очереди, позиции, пауза и
накопленный итоговый отчёт теряются. Снятая inline-кнопка может остаться снятой;
карточку можно снова открыть через `/review`, пока она доступна. Состояния
кандидатов/claims остаются в прежнем durable storage. Это ограничение выбранной
очереди без персистентности, а не обещание восстановления после аварии.

Признаки паузы зависят от существующих отчётов/логов агента: бот не добавляет новый
протокол HH. Непрочитанные вследствие ошибки файлы дают паузу. Старые события до
снимка команды игнорируются. Лог-ротация начинает чтение нового inode с начала.
