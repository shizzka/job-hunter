## 10. Reproduced blocker

### B1 — Confirmed application hidden by a surviving initial checkpoint

**Severity: BLOCKER — materially false action reporting. Confidence: high.**

Code: [`agent._observe_search`](https://github.com/shizzka/job-hunter/blob/d2cf02f2ff3286fde141012a10c0cab48426e725/agent.py#L268), [`analytics.latest_run_records`](https://github.com/shizzka/job-hunter/blob/d2cf02f2ff3286fde141012a10c0cab48426e725/analytics.py#L292), [`reporting.load_recent_run_history`](https://github.com/shizzka/job-hunter/blob/d2cf02f2ff3286fde141012a10c0cab48426e725/reporting.py#L229), `TelegramBot._recent_runs`, [`telegram_bot_ui.format_run_summary`](https://github.com/shizzka/job-hunter/blob/d2cf02f2ff3286fde141012a10c0cab48426e725/telegram_bot_ui.py#L1727).

Violated invariant: readers/Telegram must not invent `applied=0` when a confirmed workflow receipt exists; diagnostic failures must not materially falsify external-action reporting.

Minimal end-to-end sequence, run on both exact exports:

1. Invoke actual `agent.do_search` with one eligible synthetic HH vacancy and mocked matcher/client/office/notifier. Actual apply orchestration wraps the mocked native client.
2. Native client returns `{"ok":true}` and increments a deterministic native-apply counter exactly once. Actual `seen` handling succeeds.
3. Allow the initial history append, but make only the final history append raise `OSError`.
4. Read actual recent history and render it through `format_run_summary`. Separately inspect the actual application-result and search-finished journal events.

**Baseline:** business `applied=1`, one native action, `seen=applied`, confirmed `sent` event. Failed history append leaves no new history record, so no fabricated zero run is rendered.

**Candidate:** identical business result/action/state; `application_result.outcome=sent` and `search_finished.applied=1` exist. The surviving initial run record has `status=incomplete`, `applied=0`, empty funnel. Reader keeps it and Telegram renders:

```text
❌ search-… | поиск | не завершён
• Найдено: 0 | Отклики: 0 | Пропущено: 0
```

The incomplete label correctly indicates lifecycle uncertainty but does not make the stated application zero truthful. The UI does not reconcile an available receipt or mark these counters unknown.

**Independent hard-kill corroboration:** suspend actual client cleanup after one successful dispatch/`seen` commit, then SIGKILL only the isolated child. Both versions have exit `-9` and one confirmed `sent` receipt. Baseline had already persisted application count one; candidate retains only the startup count zero. Candidate remains incomplete, but still displays zero actions.

External-action/state impact: **no duplicate dispatch and no retry-state weakening** were observed; committed `seen` and the confirmed workflow receipt remain intact. The blocker is the new report falsely declaring zero confirmed actions. This is not inability to prove server-side exactly-once after an ambiguous action: the reproducer has a confirmed workflow receipt.

Existing regression test: `tests/test_observability.py::test_successful_apply_receipt_survives_protected_state_write_failure` verifies the successful final diagnostic write; lifecycle tests similarly inspect a surviving final checkpoint. They do not test a dropped/truncated final checkpoint or SIGKILL after a receipt. Independent test `test_INVARIANT_incomplete_history_must_not_claim_confirmed_apply_zero` fails on the exact candidate. The executable minimal reader test and complete end-to-end harness are included in the appendices.

## 11. Reproduced non-blockers

### NB1 — Older non-object JSON history record breaks CLI reader

Severity: NON-BLOCKING, reader/presentation regression. Confidence: high.

`reporting.load_recent_run_history` now parses every historical line and passes every parsed JSON value into `latest_run_records`, which assumes `.get`. A history file containing an old `null` line followed by six valid legacy run dictionaries reproduces it with limit five:

- baseline: returns the five recent valid dictionaries;
- candidate: `AttributeError` on the older `null`, even though all requested recent records are valid.

Telegram's `read_json_records` filters non-dictionaries, so this specific defect affects the reporting/CLI loader rather than action dispatch or protected state. No file rewrite/destructive migration occurs. Existing malformed-JSON coverage does not exercise a valid JSON scalar outside the recent window.

### NB2 — Legacy per-source keyword-stage label disappears

Severity: NON-BLOCKING, presentation compatibility. Confidence: high.

`notifier._format_source_stats({"hh":{"relevant":3}})` returns a legacy per-source stage line on baseline and an empty string on candidate. The new formatter accepts only `keyword_pass`; the reporting/Telegram history formatters have a legacy `relevant` fallback, but this notifier formatter does not. Current candidate searches provide the new field, so current matcher/apply/retry behavior is unaffected. Direct legacy callers/records lose the per-source stage display.

These non-blockers do not independently prevent freezing a safe baseline. B1 does prevent this candidate satisfying the explicitly requested action-reporting invariant.
