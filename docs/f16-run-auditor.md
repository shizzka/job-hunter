# F16 — автоматическая проверка прогонов

После каждого поиска, пробного поиска и ручного отклика аудитор читает сохранённые
данные выбранного профиля. Он не открывает HH, не вызывает ИИ и не меняет решения
об откликах. Ошибка проверки не меняет результат запуска: в журнал пишется тип
ошибки, владельцу — «аудитор не смог проверить». Отмена запуска сохраняет свою
семантику и проходит через тот же завершающий вызов.

| Правило | Что обнаруживает | Сохранённые данные |
|---|---|---|
| A01 | Чужое направление резюме, оценки или письма | Идентификаторы выбранного/запрошенного резюме, контрольные суммы входов оценки и письма, привязка письма, варианты направлений |
| A02 | Отправлена или предложена вакансия с запрещёнными условиями | Поля HH, политика направления на момент запуска; используется существующий `work_conditions.check` из B26 |
| A03 | Подходящая/ручная карточка без оценки либо с непроверенным нулём | Решения, очередь карточек, `score`, `evaluation_status`, `evaluation_present` |
| A04 | Несколько откликов работодателю за прогон или за N дней по направлению | Подтверждения/решения, работодатель из снимков переговоров, время и направление |
| A05 | Попытка отклика после остановки того же источника | Порядок `application_attempt`, `guard_stop`, `hh_breaker_stop`, `hh_ui_isolation` |
| A06 | Нет успешной проверки перед отправкой или не совпадают резюме/письмо | Трасса той же попытки: `PRE_SUBMIT_VERIFY`, `SUBMIT_CLICK`; отправки без доступной проверки |
| A07 | Отправка и подтверждение получения расходятся | `application_result`, подтверждение получения сервером/проверенная квитанция, трасса той же попытки |
| A08 | Отправлен ответ без положительной принадлежности либо с чужими фактами | Журнал чатов, сохранённая до отправки принадлежность B22 и направление фактов; старые записи «sent» без доказательства остаются непроверенными |
| A09 | Доля ошибок поставщика ИИ выше порога | `llm_call`, поставщик, результат; информационно |
| A10 | Сбои этапов, незнакомая страница, исключение запуска | `stage_failed`, `unexpected_ui`, итоговые сбои; информационно, с отпечатком |

A01/A05/A06/A08 — критические, A02/A07 — ошибки, A03/A04 — замечания,
A09/A10 — сведения. Правила независимы; ошибка одного не скрывает остальные.
Каждое замечание содержит ID правила/прогона/вакансии, название, компанию,
направление и конкретные противоречивые значения.

## Где запускается

В `agent._observe_search` — после очистки и сохранения окончательной истории и
`search_finished`, для обычного и пробного режима. В `_observe_manual_apply` —
после любого выхода из ручного отклика по карточке или `trace-apply`, включая
ранние отказы и исключения. Демон также проверяет необходимость суточной строки
при первой итерации каждого местного дня. Новые события сохраняют политику
направления, признаки условий, привязку письма и принадлежность попытки трассе.

## Что получает владелец

По умолчанию чистые прогоны проходят тихо. На следующий день — одна строка
«за сутки … прогонов N, нарушений 0», если все учтённые прогоны проверены и чисты.
Она отправляется при очередном прогоне или суточной проверке работающего демона;
при полностью выключенном процессе отправки по расписанию нет.

При замечаниях — до 10 строк, сначала критические, затем ошибки, замечания и
сведения; название/компания, ссылка и команда полного отчёта. Профили `*-dev`
проверяются тем же кодом и помечаются `[dev]`.

Канал отчёта: **только владелец** — глобальный `NOTIFY_CHAT_ID` (либо
`OWNER_CHAT_ID`) через `HUNTER_CONTROL_BOT_TOKEN`. Профильные получатели,
клиенты и список администраторов для этой доставки не используются. Если
глобальный адрес владельца отсутствует, отчёт остаётся на диске. Секреты,
тексты писем/резюме и ответы из чатов в находки не копируются.

## Команда и настройки

```bash
./run.sh --profile example audit
./run.sh --profile example audit --run search-20261022T090000-example
./run.sh --profile example audit --since 2026-10-21T00:00:00+03:00
```

Без селектора проверяется последний сохранённый прогон. Команда выводит полный
отчёт и сохраняет новые замечания, но не отправляет Telegram-сообщений и не
погашает будущую доставку владельцу. Ошибка проверки возвращает ненулевой код.

Необязательный `audit_settings.json` в домашнем каталоге профиля:

```json
{
  "send_clean": false,
  "daily_summary": true,
  "employer_days": 7,
  "llm_error_threshold": 0.5
}
```

`employer_days: 0` отключает только сравнение с прошлыми днями, проверка внутри
одного прогона остаётся. Нулевой балл после настоящей оценки разрешён. Карточки
B26 «на разбор», явно не оценённые из-за неизвестных условий, не считаются
подходящими вакансиями. Неизвестный формат не подменяется запретом; это семантика
B26. Существующий отклик работодателю не доказывает отправку в данном прогоне.

## Хранение и границы проверки

`audit_findings.jsonl` — приватный журнал находок, только дополнение; одинаковая
находка повторно не добавляется. `audit_journal.jsonl` хранит результаты проверок,
краткие резервации доставки и подтверждения уведомлений. Повторная проверка не
уведомляет об уже доставленных находках. Неудачная доставка допускает повторную
попытку; потерянное подтверждение Telegram, как и у прочих уведомлений, не даёт
гарантии ровно одной доставки при аварии процесса. Одновременные проверки
согласуют запись и резервируют доставку под короткой блокировкой без ожидания
сети внутри неё.

Исходные журналы/очереди/направления не переписываются. Пути артефактов за
пределами профиля запрещены. Корреляция трасс использует ID попытки/трассы;
противоречащие ID нельзя исправить совпадением вакансии. Старые записи без этих
ID сопоставляются только при единственной попытке/трассе. Для старых прогонов без
снимка политики используются сохранённые текущие определения направлений:
изменившиеся с тех пор настройки ограничивают точность исторической проверки.
Удалённые/повреждённые трассы и журналы дают ошибку проверки, а не зелёный отчёт.
