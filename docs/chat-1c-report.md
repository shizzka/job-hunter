# CHAT-1c: причины отказа подготовки ответа

## Локальные доказательства

Разобран только локальный материал qa-dev; запросов к hh, Telegram и моделям не было.

- `chat_responder_state.json`, чат `5700000001`, сообщение `15800000001`: попытка
  `preview` имеет `status=failed`, `draft=null`.
- `job-hunter-chat.log`, 16.10.2026 23:03:12.886: повтор `answer_grounding`
  успешен на уровне транспорта, `finish_reason=stop`.
- `telegram-bot-debug.jsonl`, 23:03:13: процесс вернул код 0 и `OK: False`.
  Бот передал `ok=true` форматтеру, который показывал «✅ … завершён».
- Успешный grounding запустил бы повторный `get_messages()` с обязательным
  ожиданием 2500 мс до проверки актуальности вопроса. Между завершением
  grounding и результатом команды прошло меньше этого времени. Значит,
  исполнение остановилось на `return answer if 0 in supported else None`;
  `_execute_reply()` превратил это в общий `LLM did not produce answer`.
  Контекстный менеджер попытки записал `failed`, CLI не напечатал `message`.

Ответ проверяющей модели не сохранялся. Поэтому исторический подтип отказа
(отрицательный вердикт, структура проверки, несоответствие чисел и т. п.)
восстановить нельзя. Утверждать, что именно неточная цитата стала причиной
живого сбоя, оснований нет. Новый журнал сохраняет подтип отказа.

## Обе гипотезы офлайн

`capture_candidate()` уже вызывает `build_salary_rule_block()`;
`CandidateSnapshot.sources` уже содержит `salary`. Этот же снимок используется
для чата и вопросов анкеты. В qa-dev заданы baseline 80000 и правило корректировки;
потери этого блока в коде чат-проверки нет, добавлять второй источник не требуется.

`test_chat_salary_rule_is_already_evidence_and_requires_literal_quotes` подменяет
обе модели фиксированными JSON-ответами и проверяет реальные источники запроса:

- ответ «Рассматриваю 80000 ₽ на руки.» с цитатой
  «Базовая планка: 80000 ₽ на руки» из `salary` проходит;
- тот же ответ с перефразированной цитатой
  «Базовая планка: 80000 рублей на руки» отклоняется как `nonliteral_quote`.

Это доказывает присутствие baseline и правила в источниках и сохранение строгой
проверки. Порог `quote_min_similarity=1.0` и алгоритм допуска ответов не изменены.

## Изменения

- Не меняя возвращаемые `str | None` / `set`, генератор и grounding передают
  диагностический код отказа. Ошибки провайдера отделены от неподтверждённых фактов,
  неполной и некорректной проверки, пропуска моделью и пустого ответа.
- CLI печатает структурированный итог без текста ответа. Telegram использует
  результат подготовки, независимо от кода завершения процесса. Для отказа —
  «Не удалось подготовить ответ: …»; для повторяемого сбоя preview — «Повторить».
  Повтор сохраняет обычное либо ручное разрешение (`allow_any`), но не отправляет
  сообщение. Для устаревшего вопроса, блокировки или неизвестного исхода отправки
  кнопка автоматического повтора не добавляется.
- Успешный preview по-прежнему доставляет сохранённый черновик с кнопками отправки
  и другого варианта. Неопределённость доставки черновика названа отдельно.
- `chat_reply_attempt` записывается при каждом результате и исключении подготовки,
  включая ранние выходы. В обычном логе — код причины и тип исключения без текста
  ответа; в приватном журнале допустимый фрагмент ответа ограничен 600 символами.
- Разделители дат отбрасываются в DOM-сборщике до классификации направления,
  даже с числовым message ID и исходящим CSS-маркером. CHAT-1b этого не закрывал.

Защиты отправки, claims, проверки ревизий/профиля, граница клика и состояния
неопределённой отправки не изменены. Живые state/env-файлы не редактировались.
